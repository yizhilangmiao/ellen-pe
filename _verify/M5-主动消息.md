# M5 · 主动消息（native 直连，不依赖前台）

> 验收日期：2026-11-03 21:49
> 环境：MuMu 实例 2 / `127.0.0.1:16448` / Android 15 / 1080×1920 / density 480
> 包：`cn.ellen.companion2` versionName `0.3.0-m4`（APK 9,011,481 B）

## 一、为什么重写（旧包缺陷）

旧包 `EllenAutonomyJobService.beginRun()` 的做法：

```
beginRun(JobParameters):
    web = new WebView(context)          // 后台藏一个 WebView
    web.loadUrl("https://localhost/autonomy.html")
    ... web 层发模型请求 ...
    finish(msg, code): if (!cancelled) notifyMessage(msg); web.destroy()
```

WebView 在后台进程里起不来（进程降级、provider trim、没有 UI 线程、启动即被回收），
整条链空转 —— **只有 App 停在聊天页时才发得出主动消息**。这就是老大反馈的现象。

另两个常量也解释了「为啥非得前台」：`nextRunAt = now + 0x1b7740`（30 分钟）、
deadline `0x3a980`（240 秒）；JobScheduler 本身在 doze 下还有额外窗口。

## 二、新实现（四层，全 native）

| 层 | 文件 | 职责 |
|---|---|---|
| 定时 | `proactive/EllenProactiveScheduler.kt` | `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP)`，间隔在 `[minGap, maxGap]` 随机，落静默时段推到结束 |
| 触发 | `proactive/EllenProactiveReceiver.kt` | 收 `ACTION_TICK` / `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` → 入队 WorkManager |
| 执行 | `proactive/EllenProactiveWorker.kt` | `doWork()` → `EllenProactiveRunner.run()`；失败也重排（一次网络抖动不该停掉节奏） |
| 出话 | `proactive/EllenProactiveRunner.kt` | 拼 prompt → `ModelHttpTransport` 直连 → 裁剪 → 写 pending → 发通知 → 重排 |
| 状态 | `proactive/EllenProactiveStore.kt` | SharedPreferences `ellen-proactive-v1` 单键 `state`（素材 / 节奏 / pending / 运行结果） |
| 取密钥 | `vault/EllenVault.kt` | 从 `noBackupFilesDir` 解 AES/GCM vault 拿 apiKey（后台读不到 web 的配置） |

**为什么中间隔一层 WorkManager**：`onReceive` 只有 10 秒，一次模型请求几十秒，直接跑会被系统掐。
Worker 有约 10 分钟窗口，且应用被杀后系统仍会把它拉起 —— 这是「后台也能发」的关键。

**为什么不用 JobScheduler 直接跑**：旧包就是 JobScheduler + WebView。定时用 Alarm（doze 下能醒），
执行用 WorkManager（可后台重启），两段都不碰 WebView。

## 三、素材怎么进 prompt

`EllenAutonomyPlugin.setContext()` 由 web 层推送（合并式写入）：

```
persona   人设（来自角色卡）
endpoint / model / threadId / apiKey（apiKey 只在 vault，不经这里）
memories[]  记忆（title + body，取自 data-heads 的 memory 类）
recent[]    最近几条聊天（role + text）
minGapMs / maxGapMs / quietStart / quietEnd   节奏
```

`buildMessages()` 拼成：

- system：人设 +「你记得这些事：」逐条 +「你们最近说的：」逐条 +「主动说一句，2–50 字，别问在吗、别解释自己是 AI」
- user：「（现在是 11月3日 21:47，你想起了他。开口吧。）」

非流式 `stream:false`，`ModelHttpTransport` 串 `open` → `read(seq+1)` 直到 `done`，
`extractContent()` 同时兼容纯 JSON 和 `data:` SSE。

### 一个字形坑

`EllenKuaiLe`（站酷快乐体）**只有 400 一个字重**，`document.fonts` 里也只有一条 `weight:"400"`。
写 `strong { font-weight: 700 }` 会让 Chromium 合成粗体，在这套圆胖字形上拖出一层灰影
（放大 2× 看得很清楚，1× 也糊）。改成 `font-weight: 400; color: var(--el-pink)` 收工。
以后任何 `font-weight: bold/600/700` 都要先确认字形有没有那个字重。

- 新增 6 个文件：`vault/EllenVault.kt`、`proactive/{EllenProactiveStore,EllenProactiveRunner,EllenProactiveScheduler,EllenProactiveReceiver,EllenProactiveWorker}.kt`。
- 新增 `plugin/EllenAutonomyPlugin.kt`：旧契约 8 方法全实现 + 本壳自加 `setContext` / `runNow` / `scheduleIn`。

## 七、坑

1. **`USE_EXACT_ALARM` 不加就白等一小时**：Android 14 起 `SCHEDULE_EXACT_ALARM` 默认拒绝，
   `canScheduleExactAlarms()` 返回 false，只能退 `setAndAllowWhileIdle`（`dumpsys` 里 `window=+1h0m0s0ms`）。
   主动消息晚一小时等于没发。加 `USE_EXACT_ALARM` 后 `window=0 exactAllowReason=policy_permission`。
2. **`am force-stop` 不能用来测后台**：force-stop 会清掉该应用的闹钟和 Job，看起来「后台发不出」，
   其实是被自己测死了。要用 `am kill`（只杀进程、保留闹钟）。
3. **`exported=false` 挡住 `adb am broadcast`**：想手动触发 TICK 会被 `Permission Denial` 拦。
   验收走 `scheduleIn` 让真闹钟触发，比开一个调试后门干净。
4. **`adb pull` 拿截图会报 `cannot create file/directory`**：用 `adb exec-out screencap -p > file`。
5. **WorkManager 让 APK 从 5.29 MB 涨到 9.01 MB**（带 room/sqlite）。后续看能否换
   `work-runtime` + `-room`，或干脆用自己的 `JobService`。
