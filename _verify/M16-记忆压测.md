# M16 · 记忆的大数据压测（5,000 条）

日期：2026-11-11 · 设备：MuMu 实例 2（127.0.0.1:16448 / Android 15 / x86_64）· 包：`app-debug.apk` 100,493,914 B · 版本 `0.3.0-m7`

## 一、为什么要单独测记忆

手记早在 M8 就用 20,018 条消息 + 503 篇压过，备份用 13,923 heads 压过并做过换机恢复；**记忆只测过 8 张卡和 6 条召回的算法对不对，从没压过量**。而记忆是「她记得我」的核心，量级会随聊天线性涨——所以补这一刀。

## 二、造数

`_临时\seed-memory.js`：5,000 条 memory（head + revision），主题在 20 个词之间轮转，**第 0 条特意做成极特殊**（「北极星吊坠 / 妈妈留下的，只在很难过的时候拿出来看」，时间戳 ≈3 年前），用来验证「很久以前的记忆还找不找得到」。

- seed 耗时 **1,230 ms**，库内 5,089 heads。
- **schema 坑**：`data-revisions` 的 keyPath 是 **`revisionId`**（不是 `id`）；head 的 `revisions` 数组里要放 **revisionId**。写错的话 `listLatest` 会当成「这个 head 没有 revision」整条跳过。

## 三、抓到两个真 bug

### bug 1 · 三个月前的记忆直接召不回来

`app\web\src\app\core\chat\recall.js` 原来每次召回都 `listLatest(kind, {limit: 300})`——只看得见最近 300 条。

5,016 条时问「你还记得我那枚吊坠吗？是什么形状的？」：

> 她答：**「我不太清楚吊坠的事。你提过吗。」**

这是老 bug ③（永远同样 7 条）的升级版：不是排序问题，是**时间早于最近 300 条的记录根本没有进入候选集**。

全量成本实测（`_临时\measure-recall-cost.js`）：读 heads 212 ms + 读 revisions 287 ms + 打分 44 ms = **544 ms**；那条老记忆在全量打分里 **rank 1、score 0.548**（第 2 名「深夜吃热食」0.218）——数据在，只是看不见。

### bug 2 · 记忆列表把 5,014 张卡一次画完

进「她的过去」：`cards 5,014`、`domNodes 60,182`、`scrollHeight 764,005 px`、**4,261 ms**。和当初手记列表一模一样的病（手记已用 60/页修过，记忆漏了）。

## 四、修法

1. **召回加索引缓存**（`recall.js`）：`INDEX_TTL_MS = 5*60*1000`、`INDEX_MAX_ENTRIES = 20000`，模块级 `indexCache = {at, entries}`；`buildIndex()` 用 `listLatest(kind,{limit:0})` 全量建一次，打分只遍历内存里的 bigram 集合。新增 `invalidateRecall()`，由写入方调用：
   - `core\memory.js`：`write()`（added/revised 时）、`createMemory`、`updateMemory`、`removeMemory`
   - `core\journal.js`：`writeJournal`
2. **记忆列表分页**（`ui\views\memory\memory.js`）：`MEMORY_PAGE = 60` + `paintMemoryRows()`，先渲染 60 张，`button.el-journal-more` 显示「再多看几条（还剩 N 条）」，点击追加 60 且不重建已渲染节点；`past` 与 `shared` 两个分支都走它。

## 五、修后实测

| 项目 | 修前 | 修后 |

| 问吊坠（首次，含建索引） | 答「我不太清楚吊坠的事」1,726 ms | **「北极星形状的，你之前说过。」** 3,799 ms |
| 第二问（缓存命中） | — | 3,323 ms |

| 她的过去首屏 | 5,014 卡 / 60,182 节点 / 764,005 px / 4,261 ms | **60 卡 / 736 节点 / 9,357 px / 2,329 ms** |

## 六、代价（写在这里免得以后被当成变慢）

- 第一次对话多约 **500 ms**（全量建索引）；**整进程生命周期只建一次**，之后每次召回打分 44 ms。
- 写记忆 / 写手记会让索引失效重建 —— 也就是「刚记下的事下一句就能召回」，代价是那一句多 500 ms。
- 内存里常驻一份 bigram 索引：20,000 条上限，量级在几 MB 内。

## 七、清场

压测数据已从设备删除：`data-heads` 5,098 → **98**、`data-revisions` 25,861 → 20,861（删掉的 5,000 条是按 `memory:stress` 前缀匹配，真记忆剩 14 条）。

## 八、还没做

- 召回质量本身仍是字面 bigram（同义改写召不回，例：「吊坠」能中、「项链」不能）——这一层要向量检索，押到后面。
- 索引没有持久化，冷启动第一条消息必付那 500 ms；可以把 bigram 索引写进 IDB 复用，但会增加写入复杂度，暂不做。
