# M11 · 记忆写入（memory 从只读变可写）

更新时间：2026-11-11 · APK 100,405,741 B · 装机 MuMu 实例 2（127.0.0.1:16448 / Android 15）

## 一、为什么要做

M0–M7 期间 `memory` 记录**只能读、不能写** —— `grep "kind: 'memory'"` 全仓零命中，记忆全靠旧包导入。
后果是「她记得我」这件事停在新壳装好的那一刻：聊得再久，她的过去也不会长。

## 二、判据（`app/web/src/app/core/memory.js`）

| 项 | 值 | 理由 |
|---|---|---|
| 新消息门槛 | 4 条 | 少于 4 句抽不出「事实」，只会抽出寒暄 |
| 间隔门槛 | 20 分钟 | 每轮都问钱受不了，而且记忆本来就该是慢变量 |
| 一次最多 | 3 条 | 宁少不多；一次抽 10 条必然混进废话 |
| 合并阈值 | 0.62 | 与老 bug ④ `__ellenMemSim >= 0.62` 对齐 |

`dueFor()` 只看 `createdAt > 上一条 memory 的 value.at` 的消息，且排除 pending/failed 与「（…」占位文本。

## 三、抽取与落库

- prompt 要求只输出 `{"memories":[{"title":"≤12字","summary":"≤60字","scope":"shared"|"past","tags":[...]}]}`，并明确「不记寒暄、不记临时情绪、不记你自己说的话」。
- 拼 prompt 时会带上**已经记过的前 30 条**（标题+摘要）并写明「不要重复记」。
- 落库前逐条与已有 80 条做中文 bigram 重叠比对（`hit / min(|A|,|B|)`）：
  - `>= 0.62` → `reviseRecord(best.headId, merge)`（summary 取更长、tags 并集、sourceIds 追加、`editedBy:'ellen'`）；
  - 否则 `appendRecord({kind:'memory', value})`。
- **模型调用与落库分开**（先算完整批、再一条条短事务），沿用老 bug ①④ 的教训。

## 四、接线

- `main.js` 的 `sendMessage()` 里在写手记之后调 `maybeRemember(...)`，失败只 `console.warn`；
- `visibilitychange` 回前台补一次；
- `window.__ellen.memory = { due, prefs, force }`（`force` 不看门槛，验收用）。

## 六、已知短板

1. **同义改写不会合并**：「壳子重写」vs「壳子修复完成」的 bigram 重叠只有 `壳子`，similarity ≈ 0.2，于是又新增一条。要真解决得上向量（旧包有 `local-embeddings`，但那套 129 MB 资产没往新壳搬）。
2. **标签没加权**：`textOf()` 把 tags 混进正文一起算，tags 命中没有被单独放权。
3. **没有人工入口**：现在只能自动抽，界面上不能改、不能删、不能手动加一条。
4. **`scope` 全凭模型判断**，`past`/`shared` 分错过一次（「他今天有点累」被判成 past 其实也说得过去）。
