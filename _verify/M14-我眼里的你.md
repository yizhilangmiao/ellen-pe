# M14 · 「我眼里的你」与「共同经历」

> 状态：代码落地完成，**实测数字待装机后填**（装机窗口由 lead 统一发）。
> 改动范围：`app/web/src/app/core/understanding.js`（新建）、`ui/views/memory/memory.js`、`ui/views/memory/memory.css`。

## 一、为什么要做

记忆写入（`core/memory.js`，M11）已经能一次从聊天里抽 1–3 条，按 `scope` 分成 `shared`（两人一起经历）与 `past`（关于他本人的事实）。但读的那一头还是空的：

| 位置 | 之前 | 现在 |
|---|---|---|
| 记忆页「我眼里的你」`state.tab === 'understanding'` | `emptyBox('这里还没有内容。')`，永远空 | 读 `kind:'understanding'` 记录，画出米白纸卡；没记录时给「还没有足够的回忆」+ 一个立刻生成的按钮 |
| 记忆页「共同经历」`state.tab === 'shared'` | 同上，永远空 | 读 `listLatest('memory', {limit:0})` 里 `scope === 'shared'` 的条目，复用 `memoryCard()` 渲染 |
| `core/journal.js` 的 `value.understanding` | 写的是空对象（`{body:'', sourceIds:[], processedIds:[], updatedAt:null}`） | 保持不动（那个字段属于手记结构）；真正的这段描述改成独立记录 `kind:'understanding'`，两者不抢同一个写入点 |

一句话：记忆攒下来了，但没有任何一处把它变成「她眼里对你是怎样一个人」的说法。

## 二、数据从哪来

- 输入：`listLatest('memory', {limit:0})` + `listLatest('journal', {limit:0})`，各取最近的 30 条 / 10 条塞进 prompt。
- 输出：一条 `kind:'understanding'` 记录，`value = { body, tags[], sourceIds[], sourceAt, updatedAt, editedBy:'ellen' }`。
  - `body`：一段第二人称描述，≤120 字（`compose()` 里硬截断）。
  - `sourceIds` / `sourceAt`：这段话是看了哪些东西写的。下次判断「过不过期」用它，不靠猜。
- 读取：`readUnderstanding()` = `listLatest('understanding', {limit:1})`，没有就返回 `null`。
- 落库：`writeUnderstanding(value)` → `appendRecord({kind:'understanding', threadId:null})`。事件溯源，追加不改。

## 三、prompt 与解析

SYSTEM（`core/understanding.js`）：

```
你替「艾莲」写一段她眼里对「他」的印象，用第二人称「你」说给他听。
只输出 JSON，不要解释：{"body":"一段不超过 120 字的描述","tags":["短词"]}
写法：具体，落到记忆里真实出现过的事（名字、习惯、他怕的东西、一起做过的事），不要空泛夸人。
不要写「你是一个善良的人」这种谁都能套的话；不许编造记忆里没有的事。
称呼他时用「你」，不要出现「用户」「对方」。tags 给 2–4 个 2–4 字的短词。
```

解析链：`ask()` → `stripFence()` → `looseJson()`（模型前后多写两句也能抠出 JSON）→ `body` 去空白后截 120 字 → 空则判失败。

失败处理（**模型调用与落库是分开的两步**，M11 老 bug ① 的教训）：

| 情况 | 返回 | 界面 |
|---|---|---|
| 没配模型 | `{status:'skipped', reason:'noConfig'}` | hint 显示「还没填聊天模型，填完再来。」 |
| 记忆与手记都空 | `{status:'skipped', reason:'noData'}` | hint 显示「记忆和手记都还是空的，先聊几句吧。」 |
| 请求失败 / 解析空 | `{status:'failed', reason:'requestFailed'|'emptyOutput'}` | hint 显示「这次没写出来，过会儿再试。」 |
| 写入异常 | `{status:'failed', reason:'writeFailed'}` | 同上；控制台 `console.warn`，不抛到界面 |

## 四、状态机

```
enter(understanding)
  ├─ readUnderstanding() 有 body ──→ [结果态] 纸卡：标题「我眼里的你」+ 正文 + 标签 + 「写于 MM-DD / 再想一想」
  └─ 没有 ──→ [空态] 「还没有足够的回忆」+ 副句 + 按钮「现在就想一想」
                │
                └ 点击 ──→ [思考态] 按钮 disabled，文案换成「正在想…」，hint 同步
                              ├─ written  ──→ load() → [结果态]
                              └ skipped/failed → 按钮复位 + hint 说明原因（空态保留）
```

- 门槛：`maybeRefresh()` 不带 force 时要求 **距上次 `updatedAt` > 24h** 且 **记忆/手记有更新（`newestAt > sourceAt`）**；按钮走 `force: true` 越过这两条。
- 并发：`running` 标志，连点只跑一次。
- 结果态里的「再想一想」也走 `force: true`。

样式（`memory.css` 末尾）：正文卡沿用 `.el-memory-card` 的米白纸 + `--z-hard-s` 硬影；正文颜色用 `--el-ink`、次要信息 `--el-paper-muted` —— 这两条在 zzz 皮肤下已被别名桥映射成 `--z-ink-paper` / `--z-ink-paper-2`（纸面深墨），所以米白纸上一定读得出来，不用另写一套 `[data-skin]` 覆盖。

## 六·五、验收手法（探针怎么写，以后都按这个来）

这一轮探针先后出现**两次假失败**，都不是功能坏了，是探针读得太早/判错容器。三条规矩：

1. **抽屉不是页面，判据不能用 `.el-page.is-active`。**
   记忆 / 相处 / 设置三个 tab 在批 3 已改成抽屉：点底栏走 `DRAWER_TABS` → `drawer.toggle(tab)`，视图 `mountInto()` 挂进 `.el-drawer .el-drawer-body`，**故意不进 `.el-pages`、不进栈**。正确判据只有：
   ```js
   const dr = document.querySelector('.el-drawer');
   const open = dr && !dr.hidden && dr.classList.contains('is-open');
   const name = document.querySelector('.ellen-app').dataset.drawer; // 'memory' | 'companion' | 'settings'
   ```
   曾经用 `.el-page.is-active === 'memory'` 判，永远不成立，于是「记忆页没打开」这种假结论连着报了两轮。
   附带坑：`toggle` 是开关，**连点两次会关掉抽屉**，探针要「只在没开时点一次」并回报 `clickedTimes` 自证。

2. **等待按「目标元素出现」判定，不要固定 `sleep`。**
   ```js
   await waitFor(() => q('.el-memory-card') !== null, 8000);      // 不是 await sleep(1400)
   ```
   根因：切页签后列表由异步 `load()` 重画，容器先挂载、卡片后填进来。固定 sleep 会读到**上一页的旧列表** —— 表现为 `shared cards 0 / matchesDb false` 的假失败（复查立刻变成 4/4）。计数类断言同理：要等「count 文案与卡片数同时变化」之后再取。

3. **验收要能自证「只做了一次」。**
   抽屉类动作回报 `waitedMs` / `afterClickMs` / `clickedTimes`；这轮 `waitedMs:0` + `afterClickMs:8` + 只点一次，比截图更能证明判据改对了。

探针本体：`E:\ailian\_临时\cdp\probe_memory.js`（已按上面三条改完：`waitFor()` 等元素、`clickedTimes` 自证、`shared.waitMs` / `understanding.waitMs` 随结果回报）。**下次别再复制旧版**，旧版用固定 `sleep` + `.el-page.is-active` 判据，会直接给出假失败。

4. **点完要校验状态，别假设「点过就等于切过去了」；而且要先怀疑产品代码，再怀疑探针。**

   现象（横屏那批）：页签元素 `isConnected:true`、无 JS 报错，连点 4 次 `activeTab` 一直是 `daily`；隔一会儿再点却一次全中。

   一开始归因成「抽屉重挂载后 handler 丢了」，**是错的**。查代码后真因在 `memory.js:524` 的
   `if (state.loading) { state.pending = true; return; }`（修复前是 `if (state.loading) return;`）：
   抽屉 `mount()` 会先自动 `load()` 拉 daily（几百篇手记，慢），此时点页签，
   handler 把 `state.tab` 改了，但 `load()` 被守卫**静默 return**；而 `paintButtons()`
   只在 `load()` 开头跑过一次，之后再没 paint —— 于是「状态变了、界面没变」。
   页签节点一次都没重建（`pages` 从不 `replaceChildren`，只有 `list` 会），handler 也从未解绑：
   `isConnected` 全 true 就是这个事实的指纹。

   修法（`memory.js`）：① click 里 `state.tab = tab` 之后**同步 `paintButtons()`**；
   ② 守卫改记 `state.pending`，在 `finally` 里「先清 pending 再补跑 `load()`」；
   ③ 页签改容器级事件委托，防将来重建 `pages` 时复发。

   **`activeAfterClickMs` 量的是什么**：它是「点下去 → `.el-segment.is-active` 这个 class 翻过去」的毫秒数，
   量的是 **DOM class 翻转**，不是网络、不是 layout、不是渲染帧。所以真机读数 `1ms`
   的含义是「反馈在 click 回调里同步发生」，**不是**「快了 1 毫秒」——旧代码这一格永远是 `daily`，
   因为那次点击被守卫吞掉、`paintButtons()` 要等整轮 daily 渲染完才可能再跑。

   **这个 bug 的用户症状**（比探针现象更重要）：改完一条记忆、点了保存，卡片上还是旧内容；
   删掉一条，列表里它还在。因为保存/删除后的刷新调用（`memory.js:555` 保存后、`565` / `585` 卡片改删后、
   `510` `think()` 里那次）走的都是同一个 `load()`，撞上正在跑的 in-flight 就被守卫静默吞掉。
   修完这三处一并变好——它们现在是「记 pending → 当前这次跑完再补一次」，不再丢刷新。

   两行关键实现，**以后别被「精简」掉**：
   ```js
   finally {
     state.loading = false;
     if (state.pending) { state.pending = false; load(); }   // 先清再跑：不自激
   }
   ```
   ```js
   if (btn && btn.isConnected) { btn.disabled = false; btn.textContent = label; }  // 只兜提前 return 的分支，按钮不卡死
   ```
   前者漏了 `pending = false` 会无限递归；后者漏了 `isConnected` 判断会往已销毁的节点上写文本，
   表现为「点了按钮永远停在『正在想…』」。

   ```js
   for (let k = 0; k < 5 && activeTab() !== 'understanding'; k++) {
     body().querySelector('[data-memory-tab="understanding"]').click();
     await waitFor(() => activeTab() === 'understanding', 2000);
   }
   ```
   即**点击 → 校验 → 重试**，把 `tries` 回报出来（这轮实测 `tries:1`；>1 就说明有重复绑定）。

5. **没有设备时，先用状态机模型自证「不丢 + 不自激」。**
   异步列表的点击被吞，这类 bug 在真机上只能看到「没反应」，很难分辨是守卫、是委托还是渲染。
   拿三十行把**同样的守卫/pending/finally 形状**单独跑一遍，比上机快得多，也更容易被下一个改这段代码的人复用：

   ```js
   const state = { tab: 'daily', loading: false, pending: false };
   async function load() {
     if (state.loading) { state.pending = true; return; }
     state.loading = true;
     try { await sleep(80); }                       // 模拟读库
     finally {
       state.loading = false;
       if (state.pending) { state.pending = false; load(); }
     }
   }
   state.tab = 'daily'; load();  await sleep(10);
   state.tab = 'understanding'; load();             // 点击发生在 daily 还没跑完时
   ```

   输出是「怎么自证」的证据链本身：

   ```
   {"loads":2,
    "paints":["start:daily","click:understanding","render:understanding","start:understanding","render:understanding"],
    "finalTab":"understanding","pending":false,"loading":false}
   ```

   - `loads:2` = 1 次原始 + 1 次补跑 → **不自激**（若 finally 里先 `load()` 再清 pending 就会无限递归）；
   - `click:understanding` 之后的 `render` 已经是 `understanding` → **点击没丢**；
   - `pending:false / loading:false` 收尾干净 → 没有残留状态把下一次点击继续吞掉。

   这个套路对任何「一个 loading 标志位管着整页重画」的容器都成立：先离线证状态机，再上机量时长。

另一条与判据同级的铁律：**别用「我觉得应该没问题」代替探针**。上面两次假失败如果按印象写「已通过」，`shared` 这个功能就会带着一个没被验证过的分支进主分支。
