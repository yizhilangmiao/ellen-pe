# M18 · 附件与麦克风权限（语音文件落盘 / 200 MB 清理 / 权限三条返回体）

> 2026-11-11 · 设备 MuMu 实例 2（127.0.0.1:16448，Android 15）· 包 100,533,188 B（21:56:00）
> 文档里的数字全部来自真机实测，不是推算。凡是「未实测」都写明了。

---

## 一、为什么要这一层

语音消息不是一条文本：一条 60 秒录音 **1.9 MB**，落 IndexedDB 会把整库撑爆（base64 还要 ×1.37），而 blob URL 重启即失效。所以拆成两半：

| 在哪 | 存什么 |
|---|---|
| 磁盘 `filesDir/attachments/` | 音频字节（原生 `EllenDocuments`） |
| IndexedDB 消息记录 | `audio: {name, uri, bytes, durationMs, peaks}` + `speech: {text, at, failed}` |

代价是**两边会不同步**：文件可能被清理删掉、被换机恢复丢掉，而消息记录还在。这一层剩下的全部工作，就是让「不同步」不以「点了没反应」的形式暴露给用户。

## 二、`EllenDocuments.list()`（原生新增，第 5 个方法）

```js
list({prefix?}) → { files: [{name, bytes, mtime, uri}], count, totalBytes, skipped, truncated }
```

- 只列 `filesDir/attachments` **一层**，不递归。
- 按 `mtime` **新→旧**：所以「删最老的」从尾部取，不用自己排。
- 上限 `MAX_LIST = 5000`，超了 `truncated: true`（只截返回值，不碰磁盘）。
- `*.part` 与子目录**不计入** `files`，只累加 `skipped`。
- 目录读不到 → 回空表，**不 reject**（调用方不用包 try）。
- `uri` 是 fileprovider 的，拿到可直接喂 `open` / `remove`。

**实测（我的清理用例）**
```
list({prefix:'voice-'}) → {count:4, totalBytes:2017584, truncated:false, skipped:0}
  files 顺序：voice-1794368378749 → …373 → …102 → …628（新→旧）
  4 条 bytes 求和 = 28204 + 25388 + 1919148 + 44844 = 2,017,584 = totalBytes ✓
listMs 4 ms（已加载 83 条消息、19 个插件的状态下）
```
**`skipped`（native-plugins 实测）**：`run-as` 造 `a-test.wav.part` + `b-test.wav.part` + `mkdir subdir-test` 后 `list({})` → `{count:1, totalBytes:28204, skipped:3}`。
**`truncated` 未实测**：要 5000 条，不能为验收往真机上灌 5000 个文件。

> **`totalBytes` 由原生求和，web 不要自己把 `files[].bytes` 再加一遍**——两处算法一旦有一处改动（比如以后排除某些前缀），就会得出两个数。

## 三、200 MB 上限与「至少留 20 条」

`app/web/src/app/core/voice-message.js`

```js
export const VOICE_MAX_BYTES = 200 * 1024 * 1024;
export const VOICE_KEEP_NEWEST = 20;
export async function voiceStorage()                    // 薄封装 list({prefix:'voice-'})
export async function pruneVoices({maxBytes, keepNewest} = {})
```

**两个闸门，先到先算**：
1. 占用 > 200 MB → 从最老的开始删，直到回落；
2. 但**永远保留最新 `keepNewest` 条**（默认 20）。

**为什么 `keepNewest` 不是 200**：一条语音 1~2 MB，留 200 条 ≈ 400 MB —— 比 200 MB 的闸门还大，等于这道闸门永远触发不了、只有条数在管。定 20 条（≈ 40 MB）既保证最近二十句一定能播，又给 200 MB 留出余量。

**为什么策略留 web**：200 MB 是产品参数，以后可能改成 500 MB 或按套餐分档；写进 Kotlin 就要为调参重编原生层。

**实测（真删除，不是 dry-run）**
```
初始                     count 4 · totalBytes 2,017,584
prune(max 1.2MB, keep 1) 删 2 条（44,844 + 1,919,148）
                          freedBytes 1,963,992 · totalBytes 53,592
                          2,017,584 − 1,963,992 = 53,592 ✓
prune(max 30KB,  keep 1) 删 1 条（25,388）· 剩 28,204 ✓
```
删不掉的单个文件跳过并继续（`console.warn`），不让一个坏文件挡住整轮清理。

**调用点**：`app/web/src/app/main.js` 启动时一次（不 await，失败只 warn）——
```js
pruneVoices().then((res) => { if (res.removed.length) console.log(...); return reconcileVoiceFiles(); })
```
冷启动实测 **`am start -W` TotalTime 948 ms**（此前基线 1,093 ms，无退化；`list()` 本身 4 ms）。

## 四、文件没了怎么办：`missing` 两处标记

删文件不动消息记录（事件溯源里改历史比留一个坏值更糟），所以靠标记：

| 时机 | 谁做 | 行为 |
|---|---|---|
| 启动 / 清理后 | `main.js` 的 `reconcileVoiceFiles()` | 拿一次 `voiceStorage()` 得到在盘文件名集合，把**已加载**消息里对不上的标 `audio.missing=true` 并落库 |
| 用户点播放、文件已没了 | `ui/views/chat/chat.js` 的 `voiceBubble().onPlay` | `readDocument` 失败 → 调 `props.onVoiceMissing(msg.id, audio)` → `appState.updateMessage` 标 missing |

气泡表现：`.el-msg-voice.is-missing` 变灰、`disabled`、`title="这条语音已清理"`。

**实测**：4 条语音消息里 3 条文件已删 → `flagged:3`、`bubbles:[missing×3, 正常×1]`，第 4 条照常可播。
截图 `_verify\shot-voice-missing.png`。

**只扫已加载消息**：收回历史页里更早的消息时不会立刻变灰，等点开播放时再标。全库扫描在 5,000 条时为几百毫秒，不值当为「翻旧账」这个低频动作付。

## 五、麦克风权限：`EllenAudio.requestPermission` 三条返回体

```js
requestPermission() → {granted, asked, blocked}
```
- `asked`：这次是否真的弹了窗（已授权时 `false`）。旧实现只回 `granted`，web 分不清「没问过」和「问过被拒」。
- `blocked`：`ActivityCompat.shouldShowRequestPermissionRationale` 为 false 且未授权 → 系统已不再弹窗，只能去设置里改。**异常时返回 true**（宁可提示去设置，也不要假装还能弹）。
- **被拒也 resolve、不 reject**：否则 web 会拿到一个没有 `code` 的异常，只能报「未知错误」。这条是踩过 `canRequestPackageInstalls()` 抛 `SecurityException` 崩进程之后的统一约定。

**实测五条（native-plugins，设备同一台）**
```
首次弹窗点允许        → {granted:true,  asked:true,  blocked:false}
已授权再调            → {granted:true,  asked:false, blocked:false}
第一次点不允许        → {granted:false, asked:true,  blocked:false}
第二次点不允许        → {granted:false, asked:true,  blocked:true}    ← USER_FIXED 置上
blocked 后再调        → {granted:false, asked:true,  blocked:true}    ← 不弹窗、不挂起，立刻返回
```
第五条是额外收获：`blocked:true` 之后调用不会像某些原生回调那样挂住，所以 web **可以放心先调、再按 `blocked` 分流**，不用先读一遍状态。

### 坑：`pm revoke` 不清 `USER_FIXED`
第一遍 `pm revoke` 后直接点拒绝，**第一次就回了 `blocked:true`**，差点当成代码错。要复现「第一次拒绝」必须先：
```bash
adb shell pm clear-permission-flags cn.ellen.companion2 android.permission.RECORD_AUDIO user-fixed user-set
adb shell pm revoke cn.ellen.companion2 android.permission.RECORD_AUDIO
```
测完同样两步 + `pm grant` 还原，否则下一个人静默被拒、以为是 App 坏了。
判定：`dumpsys package cn.ellen.companion2 | grep RECORD_AUDIO` 看 `flags=[ USER_SET|USER_FIXED|…]`。

### 另一个坑（早期踩的，一并记）
`RECORD_AUDIO` 重装后默认 `granted=false`，此时**按住说话全程无反应、界面无提示**。现在切成语音态会先 `ensureMicPermission()` 预请求，弹窗期间 HUD 保持 hidden（不误亮「正在录音」）。

## 六、与其他模块的契约

- **导出/备份**：`manifest.files[] = {id, name, sha256, sizeBytes, mimeType}`，上限 100 MB、新的优先；`media.mode = files.length ? 'include' : 'metadata-only'`。字节**不过 JS 桥**（原生按 name 直读磁盘）。
- **原生备份侧**：`backupWrite` 在附件已全部写完时回 `BACKUP_NOTHING_PENDING` —— **web 不许再喂 write**（会往容器尾巴追加、包坏）。这是契约，不是坑。
- **导入**：同名文件不覆盖（同 sha 算 `restored`，不同 sha 进 `keptFiles`）。
