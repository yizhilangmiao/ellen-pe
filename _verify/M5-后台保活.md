# M5 · 后台保活（EllenBackground）

> 目标：**发完消息就切走，她也要把那句话说完。**
> 判据不是「没有白屏」，是「切到桌面以后回复照样落库，且进程没被回收」。

## 一、旧包为什么需要它，新包为什么也需要

旧包 `EllenBackgroundPlugin`（39,175 B smali，30 方法 / 11 个 @PluginMethod）不是主动消息，
它是**前台保活**：常驻通知 + 让 WebView 进程别被系统回收。

新包同样需要，理由一样：web 层跑在 WebView 里，Activity 一进后台，系统随时能回收进程，
流式回复断在半截 —— 界面显示「正在说」，切回来发现只剩半句，或者整段没了。
主动消息那条链（`EllenAutonomy`）已经全 native，不依赖 WebView；**这条是给聊天用的**。

## 二、实现（四层）

| 层 | 文件 | 干什么 |
|---|---|---|
| 服务 | `app\app\src\main\java\cn\ellen\companion2\background\EllenBackgroundService.kt` | `startForeground(0x4b3, ...)`，`foregroundServiceType=dataSync`，channel `ellen-background-v1` |
| 插件 | `app\app\src\main\java\cn\ellen\companion2\plugin\EllenBackgroundPlugin.kt` | 11 个契约方法 + 状态仓库读写 |
| web | `app\web\src\app\core\background.js` | `keepAlive(on, extra)` / `withKeepAlive(task)` / `takeChatReply()` |
| 接线 | `app\web\src\app\core\chat\session.js` | `send()` 开头 `keepAlive(true,{replyActive:true})`，`finally` 里 `keepAlive(false)` |

**通知长什么样**（IMPORTANCE_LOW、无声、`setOngoing`、不可划掉）：

| 状态 | 文案 |
|---|---|
| `replyActive` | 在想这句话 |
| `mediaActive` | 在念给你听 |
| `organizationActive` | 在整理手记（done/total） |
| 都不亮 | 在这里 |

标题固定「艾莲」，小图标 `ic_ellen_notify`（粉色心形），颜色 `0xE4B8CD`。
落在系统的「静音」分组里，不响不震。

## 三、契约（11 方法，全实现）

| 方法 | 行为 |
|---|---|
| `update({sessionId,threadId,replyActive,mediaActive,paused,organizationActive,organizationTotal,organizationDone,organizationProfileId})` | 校验 id 正则（`[A-Za-z0-9._:-]{1,160}` / `{1,200}` / `[A-Za-z0-9_.:-]{1,180}`，不合法 → reject `INVALID_BACKGROUND_WORK`「后台任务归属无效。」）；`closed=true` 时 reject `BACKGROUND_CLOSED`「后台服务已关闭。」；有活就起服务，没活就停 |
| `state()` | `{running, wanted, paused, closed, sessionId, threadId, replyActive, mediaActive, organizationTotal/Done, updatedAt, lastError, notifications}` |
| `stop()` | 撤前台 + 停服务（不设 `closed`，下次还能起） |
| `close()` | 同 `stop` 但设 `closed=true`，之后 `update` 一律 reject |
| `requestPermission()` / `requestInitialPermission()` | 有权限直接 `{notifications:'granted'}`；没有就打开系统通知设置页并返回 `prompt` |
| `notificationSettings()` | 打开 `ACTION_APP_NOTIFICATION_SETTINGS`（失败退 `ACTION_APPLICATION_DETAILS_SETTINGS`） |
| `messageArrived({text,threadId})` | 写进 `EllenProactiveStore`（`pendingType='chat'`）+ 弹一条通知；回复在后台到齐时用 |
| `messageContext()` | `{threadId, sessionId, updatedAt, running}` |
| `consumeOpen()` | 取 `pendingType==='proactive'` 那条（不匹配不取） |
| `consumeMessageOpen()` | 取 `pendingType==='chat'` 那条 |

**收件箱只有一个**（`EllenProactiveStore` 的 `pendingText/pendingAt/pendingType`），
两种待读靠 `type` 区分，互相不会吃掉对方的。

## 四、验收证据（MuMu 实例 2 / Android 15 / APK 9,011,783 B）

### 1. 服务真在前台（`dumpsys activity services`）
```

    isForeground=true foregroundId=1203 types=0x00000001
    foregroundNoti=Notification(channel=ellen-background-v1 ... flags=ONGOING_EVENT|NO_CLEAR|FOREGROUND_SERVICE
                                color=0xffe4b8cd category=service)
```
`types=0x00000001` = `FOREGROUND_SERVICE_TYPE_DATA_SYNC`。

### 2. 真发送时 FGS 被系统放行（logcat）
```
13:26:11.210  Capacitor: pluginId: EllenBackground, methodName: update
              {"sessionId":"s-mw1o691b-j7mc9m", ..., "replyActive":true}
13:26:11.211  ActivityManager: Background started FGS: Allowed
              [callingPackage: cn.ellen.companion2; uidState: TOP; targetSdkVersion:36]
13:26:13.298  Capacitor: pluginId: EllenBackground, methodName: update   ← finally 里的 keepAlive(false)
13:26:13.299  ActivityManager: Stop FGS timeout: ServiceRecord{...EllenBackgroundService}
```
`uidState: TOP` 这行是关键：**FGS 只能在前台启动**，所以 `keepAlive(true)` 必须发生在 `send()` 开头
（用户还在界面上），不能在后台补。

### 3. 切到桌面后回复照样落库
```

t+0.5s  dumpsys 里 isForeground=...    ← 服务在跑
t+12.5s no EllenBackgroundService       ← 说完自己停了
回到前台 state().messages = 14 条
  user: 我在楼下买了点橘子，等下上楼。
  assistant: 橘子挺好的，回去剥一个，配点吃的。\n\n上楼先看看豆豆开饭没，顺便你也歇一下。
```
中间没有重新启动进程（`pid 6672` 全程不变）。

## 五、坑（都踩过）

1. **`Background started FGS: Disallowed ... uidState: LAST`** —— App 已经在后台时调 `update({replyActive:true})`
   必然失败。这不是代码错，是 Android 12+ 的硬限制。所以 `start()` 现在**如实返回布尔值**：
   失败就把 `running` 置 false 并把 AMS 原话写进 `lastError`，别让界面以为还活着。
2. **`Stop FGS timeout` 这条日志会一直在，但不代表出事。** 停服务时 logcat 会出现
   `ActivityManager: Stop FGS timeout` + `ForegroundServiceTypeLoggerModule: FGS stop call for: ... has no types!`，
   但通知中心里那条常驻通知**确实被撤掉了**（截图 `shot-m5-bg-after-stop.png` 是「无通知」）。
   原因是「不再前台」和「服务销毁」几乎同时发生，系统记账时 types 已经清了。
   做法上仍然先撤前台再退：`ACTION_STOP` 分支里 `ServiceCompat.stopForeground(STOP_FOREGROUND_REMOVE)`，
   `onDestroy()` 里再兜一次。**别拿这条日志当失败判据**，要看通知是否真的消失。
3. **`.el-composer-input` 是错的类名**，真正的是 `.el-composer-field`。验收脚本第一次写成前者，
   `document.querySelector` 返回 null，却被 `|| document.querySelector('textarea')` 兜住了，
   看起来「发成功了」，其实点的是兜底分支 —— 别让兜底掩盖选择器错误。
4. **回复太快就看不到 FGS 在跑**：模型 2 秒答完，采样窗口只有 2 秒。要么连拍两次 dumpsys，
   要么直接看 logcat 的 `Background started FGS: Allowed` 时间戳。
5. **FGS 类型必须声明在 manifest**：`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` 两个权限
   + `<service android:foregroundServiceType="dataSync">`，缺一样就崩在 `startForeground`。

## 七、还没做

- **`mediaActive` 目前没有调用方**：语音播报（M6）接进来以后才用得上。
- **`organizationActive` 同理**，等手记批量整理（M5 后续）接。
- **没有做「切回来时把后台到齐的回复补进界面」的端到端验证**：`drainChatReply()` 已经写进 `main.js`
  的启动/`visibilitychange`/`focus` 三处，但只有在「native 侧真的走了 `messageArrived`」时才触发，
  而现在的聊天回复是 web 自己收流、没经过 native，所以这条路径暂时是空跑。
- 通知点开只是回到 App（`MainActivity`），没有「点哪条就跳到哪条消息」的定位。
