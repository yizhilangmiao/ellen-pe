# M18 · 旧包与压缩包盲区扫描（2026-11-11）

## 为什么扫这个

盘上「压测」这个词的命中面之前是人工 `find` + `head -30` 得出的，前几条全是 `lora_ellen\.venv` 的噪音，把真正的条目挤掉了。当时的结论是「压测脚本只有 `_临时\` 里那几份」，但**压缩包与 APK 里的内容从来没有被打开看过** —— 文件名不含「压测」，不代表里面没有。这一篇把这块关掉。

## 怎么扫的

两遍，第二遍才是关键：

1. **文件名**：`unzip -l <包> | grep -iE "stress|seed|measure|压测"`
2. **文件内容**：把每个 APK 里的 `assets/**/*.js` 逐个 `unzip -p` 抽出来，`grep -c "memory:stress"`（压测造数的唯一标记串）

只做第 1 遍是不够的 —— 压测脚本就算被打进包里，文件名也只会是 `index.js` / `chunk-xxx.js`。

## 结果

| `assets/*.js` 内容含 `memory:stress` | **0**（16 + 25 + 26 = 67 个 js） |
| 两个导入工具包里含压测脚本 | **0** |

`聊天记录导入工具.7z` 里是 `使用说明.txt` / `导出聊天记录.bat` / `恢复聊天记录.ps1` 三个文件，与压测无关。

## 结论

**旧包里没有任何压测脚本或压测造数代码。** 原因也清楚：压测脚本从 `_临时\` 走 CDP 直接注入运行时，从来没被 `import` 进 `app\web\src`，构建产物里自然不会有。

所以「压测能力只存在于 `_临时\`」这个判断成立，也所以 `_临时\` 一清理、一自动清空，压测能力就归零 —— 这正是新建 `_压测\` 的理由（该目录不在 `.gitignore` 的忽略名单里，git 直接能收）。

## 顺带发现：库里躺着 20,710 条孤儿 revision（已核实）

扫包时数到当前库是 **107 个 heads / 20,874 个 revisions**，比例异常。写了个一次性探针（`_临时\chk-orphan.mjs`）逐条核对，结论不是猜测：

| 项 | 数 |
|---|---|
| heads | 107 |
| revisions | 20,877 |
| 仍被某个 head 的 `revisions[]` 引用 | 167 |
| **孤儿（head 不存在、也没人引用）** | **20,710** |
| 其中 message / journal / memory | 20,000 / 704 / 6 |
| 重复 revisionId | 0 |
| 最新的孤儿落于 | 2026-11-10 |

（167 + 20,710 = 20,877，对得上。数字每次跑会小幅变动，因为正常聊天在写库。）

样本：`revisionId: "m8-rev-0"`、`headId: "memory:m8-0"` —— 名字直接写明是 M8 那轮压测造的。

**成因**：`_临时\m8-*.js` 那批清场脚本只删 `data-heads`，不删 `data-revisions`。所以库里「看得见的」只有 107 条，真正占地方的是 20,710 条谁也读不到的残骸。

**影响**：备份按 heads 走，包里不含它们，所以 M7 那轮的数字没被污染；但库体积、`getAll(data-revisions)` 这类全表操作、以及未来任何「扫全表」的逻辑都会被这 2 万条拖住。

**已备工具、未执行**：`_压测\page\purge-orphans.js`，默认 dry-run，「head 不在 + 没人引用」双条件才删，500 条一事务。清不清等拍板 —— 这是真实数据，虽然证据确凿是垃圾。
