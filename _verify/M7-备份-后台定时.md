# M7 · 备份的后台定时（native 侧）

> 2026-11-11 · 会话 native-plugins · MuMu 实例 2 `127.0.0.1:16448` / Android 15 / 1080×1920
> 新建：`app\app\src\main\java\cn\ellen\companion2\proactive\EllenBackupWorker.kt`
> 接线：`app\app\src\main\java\cn\ellen\companion2\plugin\EllenArchivePlugin.kt`（4 处调用 `scheduleNext`）
> 包：`app-debug.apk` 100,493,914 B（2026-11-11 17:24:33，普通构建，含 web）

## 一、为什么需要

备份原来只在两处检查：启动 App、回到前台（web `core/backup.js` 的 `autoRun()`）。
**用户几天不开 App，就一次都不会备份** —— 备份开关写着「每 7 天自动存一份」，实际只在开 App 那一刻兑现。
数据只有手机里一份，用户还以为自动备份在跑。这就是这条链要补的缺口：**后台到点提醒**。

## 二、为什么不能在这里跑 JS

M5 已经付过一次学费：旧包 `EllenAutonomyJobService.beginRun()` 在后台 `new WebView(context)` 加载
`autonomy.html` 再让 web 发请求，结果**后台进程起不了 WebView**（进程降级、无 UI 线程、启动即回收），
整条链空转，只有 App 停在聊天页时才发得出主动消息（见 `_verify\M5-主动消息.md` 第一节）。

备份更麻烦一层：**包的内容原生拿不到**。manifest JSON 是 web 用 IndexedDB 现算的
（`core/store/export.js` 的 `buildManifest()`），原生只有 `BackupWriter` —— 它负责「按 manifest 把字节
写进容器」，没有 manifest 就写不出包。想原生直接写包，等于把整套数据层复制一遍，那是 M3 的事。

所以这一版的分工是：

```
WorkManager 到点  →  发一条通知（不碰数据）
用户点通知        →  App 回前台
web autoRun()     →  due() 判该备了 → run() 真写包 → commit 写 nextAt
```

**后台只叫醒用户，不替用户干活。** 这不是妥协，是这条链唯一能保证正确性的分工。

## 三、实现

| 位置 | 做了什么 |
|---|---|
| `proactive\EllenBackupWorker.kt`（新建） | `Worker.doWork()`：读 state → 判到点 → 发通知 → 排下一次 |
| `EllenArchivePlugin.configure` | 开关/间隔变了 → `scheduleNext()`（关掉时它自己 `cancel`） |
| `EllenArchivePlugin.chosenDirectory` | 刚选完文件夹 → `scheduleNext()` |
| `EllenArchivePlugin.backupCommit` | 备份成功、nextAt 已推进 → `scheduleNext()` |
| `EllenArchivePlugin.backupCall("state")` | App 起过一次就补排一次（老状态里可能根本没排过） |

排期方式复刻主动消息那条链：`OneTimeWorkRequestBuilder.setInitialDelay(delay)` +
`enqueueUniqueWork("ellen-backup-tick", ExistingWorkPolicy.REPLACE)`。

四个关键取舍：

1. **用 WorkManager 的 delay，不用 AlarmManager**。7 天这种长间隔，WorkManager 的延迟**重启后仍然有效**
   （自己维护 nextAt，不用再补 `BOOT_COMPLETED`）；主动消息用精确闹钟是因为它要分钟级准时。
2. **到点后故意不动 `nextAt`**。web `due()` 的 `timeUp = !nextAt || now >= nextAt` 全靠它；
   一动就等于「把这次备份提前吃掉」，用户开 App 也不备了。真正推进 `nextAt` 的只有 `commit`。
3. **同一个到点时刻只提醒一次**。prefs 记 `notifiedFor`（= 提醒过的那次 `nextAt` 值）；
   用户不理就 12 h 后再排一次 —— 一天最多两条，不会变成骚扰。
4. **到点时间三级回退**：`nextAt` → `lastSuccessAt + intervalDays×86400000` → `now + intervalDays`。

## 四、实测（16448，2026-11-11 17:24–17:33）

测法：`run-as` 直接写 `shared_prefs/ellen-backup-v1.xml`，把 `nextAt` 设成**设备时间 −60 s**，
重启 App 让 `state()` 补排一次，然后等 Worker 自己触发。

| # | 项 | 实测证据 |
|---|---|---|
| 1 | 排上了 | `dumpsys jobscheduler` → `SystemJobService ... u0a52/0 ... TIME=+2s640ms` |
| 2 | 真跑了 | 同一段历史 → `START: #u0a52/0 ...`（22 s 前） |
| 3 | 发了通知 | `dumpsys notification --noredact` → `android.text=String (该备份了，打开艾莲我自动存一份)`、`channel=ellen-backup/备份提醒`、`category=reminder`、`AUTO_CANCEL`、`color=0xffe4b8cd`；截图 `_verify\shot-backup-worker.png` |
| 4 | 自己重排 | 新 job `TIME=+11h59m37s553ms`（RETRY_MS 12 h）；prefs `notifiedFor=1794357484000` |
| 5 | **nextAt 没被改** | `nextAt` 与 `notifiedFor` 同值，仍是过去时间 → 用户开 App 时 `due()` 仍判「该备了」 |
| 6 | 点通知进 App | `input tap 540 900` → `topResumedActivity=cn.ellen.companion2/.MainActivity` |
| 7 | `am kill` 后仍触发 | pid `26632` → `26805`（系统为跑 job 重新拉起进程）；`notifiedFor` 变新值 `1794357566000`；通知再次出现；截图 `_verify\shot-backup-worker-kill.png` |
| 8 | 关开关撤排期 | `backupCall configure {enabled:false}` → 返回 `{enabled:false, nextAt:0}`；jobscheduler 历史 `STOP: #u0a52/2 ... canceled` |

`am kill` 用的是 `am kill`（保留 Job/闹钟），不是 `am force-stop`（会清掉）—— 和 M5 那条结论一致。

## 五、坑

1. **MuMu 的设备时钟比宿主慢 8 h 47 m**。`adb shell date` 报 `08:37`，宿主是 `17:24`。
   用宿主时间写 `nextAt` → Worker 算出 `Minimum latency: +8h48m34s`，看着像「根本没生效」。
   **测法必须用 `adb shell date +%s` 取设备时间**，别用 PowerShell 的 `UtcNow`。
2. **`POST_NOTIFICATIONS` 默认 `granted=false`**（重装后重置）。`notify()` 抛 `SecurityException` 被吞掉，
   表现是「job 跑了、`notifiedFor` 写了、通知栏什么都没有」，很容易误判成 Worker 没跑。
   测前 `adb shell pm grant cn.ellen.companion2 android.permission.POST_NOTIFICATIONS`。
   真机上这权限得靠首次启动的授权弹窗，代码里已经做了「没权限就静默降级」（下次开 App 照样备）。
3. **`databases/androidx.work.workdb` 是 0 字节**，别拿它当「有没有排上」的证据。
   看 `dumpsys jobscheduler` 里 `cn.ellen.companion2/androidx.work...SystemJobService` 的 `Minimum latency`。
4. unique work 名字必须和主动消息分开（`ellen-proactive-tick` / `ellen-backup-tick`），
   否则 `ExistingWorkPolicy.REPLACE` 会把对方顶掉。
5. `am start` 之后 CDP 有时连不上（`ws error: unknown`）：先把 App 拉到前台再 `forward`，
   进程被 job 重启过的话，`webview_devtools_remote_<pid>` 里的 pid 必须重取。

## 六、还没做

1. **web 侧一个字没改**（本任务不动 `app\web`）。`autoRun()` 的触发点还是原来的「启动 + 回前台」。
2. 点通知进来只回前台，没有额外提示；将来可在聊天页顶部加一句「刚给你存了一份」。
3. **真机（vivo）未验**：通知权限首次弹窗、厂商省电策略掐掉后台后的补跑。
4. 备份成功后没清 `notifiedFor` —— 不需要（`commit` 会把 `nextAt` 推到新值，值自然不同）；
   唯一边界是用户手动把 `nextAt` 改回同一个值，会不提醒。极端情况，接受。
