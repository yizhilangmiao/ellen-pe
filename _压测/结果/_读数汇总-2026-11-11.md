# 四类大数据压测 · 读数汇总（2026-11-11）

设备：MuMu 实例 2（`127.0.0.1:16448`，艾莲 pid 每轮都变，本轮 34101）· 库 `cn.ellen.companion2` · 每轮跑完清场复原
（压测库是模拟器上的测试库，`profile:old-device`，不是真机 `3422813346000RJ` 的记录）

## 一、结果对照

| 类 | 场景 | 本轮实测 | 历史基准 | 判定 |
|---|---|---|---|---|
| 记忆 | `memory-5000` 造 5,000 条 | 造数 1,650 ms · 列表 60 卡 2,409 ms · 翻页 85 ms | M16：seed 1,230 ms · 首屏 2,329 ms · 翻页 60 ms | 同量级 |

| 日记 | `journal-503`（2 万消息 + 503 篇） | 造数 6,062 ms · 判该不该写 223 ms · 查今天 227 ms · **写一篇 2,593 ms** · 首屏 100 ms | M8：2,608 ms · 19 ms · 18 ms · 201 ms | 写一篇吻合；**判/查慢 12 倍，见发现三** |

记忆、日记、备份三类都能在自动化里跑通并复原；**回忆的首问**和**日记的判/查**这两处，实测比历史基准慢一个量级。

## 二、发现

### 一、召回首问慢在事务个数，不在数据量 —— 已用旁路修掉

`core/store/library.js:51` 的 `listLatest` 对每条 head 单独 `getOne` —— 5,020 条就是 5,020 个事务。按独立事务口径抽样外推 **1,971–3,268 ms**；同样的读收进**一个事务**只要 200–300 ms。差 6–10 倍。

M16 报的 544 ms 与「单事务分解」同口径，不代表真实链路。

**处理方式：都不删、绕过去。** `library.js` 是公共读路径（记忆页 / 备份 / 聊天历史都走它），一个字没动；召回在 `core/chat/recall.js` 里自己开了旁路 `readLatestOneTx(kinds)` —— 一个事务读完 heads + 所有 head 的末条 revision，失败自动回退老的 `listLatest`。

等价性不是推的，是量的：`page/probe-batch-read.js` 把两套读法都复刻一遍，在同一份 5,018 条数据上跑：

| kind | 条数 | 逐条事务 | 单事务 | 倍数 | 条数/顺序/headId/revisionId |
|---|---|---|---|---|---|
| memory | 5,018 | 2,688 ms | **297 ms** | **9.05×** | 全等 |
| journal | 3 | 15 ms | 7 ms | 2.14× | 全等 |

改完构建装包（`app\build-apk.ps1` → `adb install -r`），memory-5000 跑了三轮：首问 **265 / 413 / 378 ms**，五项判定全 PASS（吊坠仍第 2 名、首屏仍 60 卡，说明数据真读到了，不是「快得不正常」）。

副产物：按 revisionId 精确取，天然不碰库里那 20,710 条孤儿 revision。

### 二、「吊坠必须排第 1」这条基准要改

真实库里有两条更贴题的记忆：`吊坠形状` 0.924、`嗓子疼和吊坠` 0.638，压测种子 `北极星吊坠` 0.548 排第 3（真实链路）/第 2（纯字面分，时间加权把「嗓子疼和吊坠」抬上来）。

不是退化，是基准定错了。`run.mjs` 已改成「前 3 名内」。

### 三、`journalDue` / `todayJournal` 每次 230–320 ms

2 万条消息下连调三次：`due` 237 / 317 / 258 ms，`today` 252 / 280 / 248 ms —— **不是冷启动，每次都慢**。

M8 记的 18 / 19 ms 在同量级数据下复现不出来。判该不该写是每条消息前都会走的路，这块直接影响聊天手感。待查是否在扫全表。

### 四、备份整包在模拟器上自动跑不了

`backup.run()` 有四个前置门槛，`directory` 为空直接 `skipped=noDirectory` 返回，3 ms 就结束 —— 那不是「备份很快」，是压根没备份。

目录是 SAF 授权，必须人点一次系统选择器。所以 **manifest 组包能自动测（7.83 MB / 13,928 条），写盘那一段只能手工验**。probe 现在会把 `skipped` 原因打出来，不再拿 3 ms 去对 500–3000 的基准。

## 三、事故记录：误删一条日记（已确认不可恢复）

`probe-journal.js` 调 `journal.force()` 量「写一篇」的耗时。`writeJournal` 按天找 head —— **今天已经有日记就复用那个 head 追加一条 revision，不新建**。所以 `force()` 返回的 `headId` 是**今天那篇真实日记**。

当时想让 `clean.js` 顺手把这条清掉，给它传了 `headIds`。清场按 id 删，把整条日记（head + 3 个 revision）删了。

- 发现时立刻停止后续跑批
- `adb pull` 出整个 `https_localhost_0.indexeddb.leveldb`（15 个文件 / 12.6 MB），逐文件二进制搜三个 revisionId —— **零残留**，compaction 已经吃掉了
- 库里现在 108 heads / journal 3 条，比事故前少一条

两处已修：

- `probe-journal.js` 写完立刻自回滚（删 revision + `head.last` 指回原条；head 本来就空就连 head 一起删），只留耗时数字
- `clean.js` 删掉 `headIds` 参数，**只按前缀删，永不接受精确 id**

被删的是模拟器测试库里的一条（`journal:old-j` 同批的测试数据），不是真机记录。但机制上的错是真的：任何「按 id 删」都会指向真数据。

## 四、顺手核实的两件事

- **孤儿 revision 20,710 条**（message 20,000 / journal 704 / memory 6）。`_临时\m8-*.js` 那批清场只删 heads 不删 revisions。工具 `page/purge-orphans.js` 已备（默认 dry-run）。**决策：不删，绕开。**
  - 已绕开：召回旁路按 revisionId 精确取，不扫全表；备份（`core\backup.js`）只 `count` 不读全表。
  - **还有一个没绕开的**：导出 `core\store\export.js:179` 的 `readAll(STORE_REVISIONS)` 会全表读一遍，再按 `headIds.has(r.id)` 过滤掉孤儿。实测 20,875 条：读 250 ms、序列化后 6.8 MB，其中 **99.2% 是白读**。包内容不受影响（孤儿本来就被过滤掉），只是慢。
  - 没动它的原因：导出是数据安全路径，改取数方式要连导入一起验。真要改的话正确做法是——先 `readAll(heads)`，按每个 `head.revisions[]` 的 id 精确取（一个事务），结果集应当与现在**完全相同**，对账依据是 manifest 里 `records` 条数不变。
- **旧 APK 里没有任何压测代码**（3 个包共 1,495 条目、67 个 js 全扫，0 命中），见 `_verify\M18-旧包扫描.md`。
