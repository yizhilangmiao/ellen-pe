## 一、结论（先看这几行）

1. **注册插件 27 个**：22 个 `Ellen*` 自有插件 + `App` + `SystemBars` + `WebView` + `CapacitorCookies` + `CapacitorHttp`。
2. **真实 `@PluginMethod` 184 个**：自有 `Ellen*` 插件 **158 个**（`EllenMini` 那 11 个已排除）+ 自带/社区插件 26 个（`App` 7 / `CapacitorHttp` 6 / `CapacitorCookies` 5 / `SystemBars` 4 / `WebView` 4）。其中 82 个带 options，102 个空参。
3. **`EllenMini` 是死插件**：smali 里有类、有 11 个 `@PluginMethod`，但运行时 `PluginHeaders` 里没有它，全 dex 也没有 `registerPlugin(EllenMiniPlugin)`。M2 不重写它。
4. **旧方案里写的「21 插件 / 152 方法」是错的**，那是 10-28 的旧 smali 副本（少了 `EllenDiagnosticsPlugin`、`EllenModelHttpPlugin`，也没有 `SystemBars`/`WebView`）。以本文件为准。
5. **旧 web 从不调用** `SystemBars` / `WebView` / `CapacitorHttp` / `CapacitorCookies`（4 个 chunk 里名字出现 0 次）。M1 只接 `App`，这四个随 Capacitor 默认带不带都行，不实现业务。
6. 事件面 **12 个事件名**，分布在 11 个插件；5 个插件共用 `event`，靠 payload 的 `type` 区分，别按事件名分流。

## 三、必须复刻的调用语义（比方法名更容易漏）

旧 web 层不是直接 `Plugins.EllenMedia.pick()`，而是走一个统一派发器（产物里叫 `S2`），形态：

```js
S2(plugin, `startRecording`, { recordingId, fileId, maxDurationMs },
   { signal, cancelMethod: `cancelRecording`, cleanup: true, disposeResult: (r) => ... })
```

新 web 层必须逐条复刻这 5 个语义，否则「取消 / 超时 / 失败清理」会退化：

1. **AbortSignal 中断**：signal abort 后要么调 `cancelMethod`，要么干净 reject，不能让 reader 挂着。
2. **cancelMethod**：`pick`/`pickAlbum`/`captureScreen`/`pasteImage` → `cancel`；`startRecording` → `cancelRecording`；`requestStream` → `cancelStream`（见各方法契约）。
3. **cleanup**：`cleanup: true` 的方法（`cancel`、`releaseSelections`、`discard`）在失败路径上必须最终执行，且失败要收集为 `AggregateError`。
4. **disposeResult**：拿到结果先做资源释放（如 `releaseSelections(result.files)`），再交给业务层。
5. **requestId**：几乎每个长操作都带 `requestId`（`call-probe-capability` 之类前缀 `newId(prefix)` 生成），对端用它做幂等取消，别用序号自造。

## 六、持久化（运行时实测，b17）

IndexedDB 有两个库：

| 库 | 版本 | store | keyPath | 索引 |
|---|---|---|---|---|
| `ellen-mobile-data-v1` | 3 | `data-meta` | `key` | - |
| | | `data-profiles` | `id` | - |
| | | `data-heads` | `id` | `kind`, `messageTime`, `profileId`, `profileKind`, `profileKindThread` |
| | | `data-revisions` | `revisionId` | `messageOrdinal`, `recordId` |
| `ellen-mobile-reading-anchors-v1` | 1 | `anchors` | `key` | - |

记录是**事件溯源**结构：

```
data-heads:     { id, kind, profileId, revisions:[revisionId...], conflict, deleted, threadId, createdAt, threadKeys[] }
data-revisions: { id, kind, profileId, revisionId, parents[], origin{}, at, deleted, value, refs[] }
data-meta:      { key:"main", storageVersion, generation, deviceId, bindings, commitId,
                  migratedFrom, legacyGeneration, scopeEpoch, scopeVersions }
data-profiles:  { id:"profile:<uuid>", characterId, createdAt }
```

- 记录 id 形如 `emotion:ellen-configuration-application:<hash>`、`thread:<uuid>`，`kind` 是 `emotion`/`thread`/…（首段即 kind 前缀）。
- **迁移要按 revision 粒度搬，不是按 head 搬**——head 只存 revisionId 列表，值在 revisions 里。
- localStorage 另有 `ellen-leave`（启动自检串）、`ellen.mobile.bond.v1`（羁绊进度）、`ellen.diaglog.v2`（诊断日志，45 KB 级）。
- 模拟器只有 4 条记录，**只能验 schema，验不了真实数据形状**；真实形状要用老大手机上的 b17 导出包核对。

## 九、契约修正（M2 施工中发现，**以此为准**）

抽取器（`_tools\dump_plugins.py`）把「取默认值的字符串」当成了「键」，凡 `call.getString("键", "默认值")` 都多抓一个假键。
M2 逐行对读 smali 后确认的修正如下，未整改的抽取结果一律以本节为准：

| 插件.方法 | 契约里的 options（错） | 真实 options |
|---|---|---|
| `EllenSecureConfig.read` | `model` | `scope`（默认 `model`） |
| `EllenSecureConfig.write` | `model, value` | `scope, value` |
| `EllenSecureConfig.remove` | `model` | `scope` |

规律：**同名假键必与真实键的默认值相同**。后续插件逐个核，修正表继续往下加。

reject 的「消息 / 码」顺序也要注意：旧码统一是 `call.reject(中文消息, 错误码)`，
抽取时按「键」记录的其实是**错误码**，中文消息在 `messages` 里。
